# V0.10 — Live Candidate Reconciliation Boundary

V0.10 begins the live scanner → candidate reconciliation → scheduler phase.

## Boundary

The live capture path now performs:

`LiveMapScanner → LiveActionCandidateReconciler → ActionScheduler → ActionOrchestrator`

The reconciler is a pure, diagnostic/scheduling-input component. It does not dispatch gestures and has no lifecycle or recovery authority.

## Eligibility

A candidate crosses the boundary only when the existing `LiveActionCandidatePolicy` accepts it:

- current camera continuity is valid;
- validation is safe;
- validation stage is `SAFE_TO_INTERACT`;
- planner rank is valid;
- planner score is finite.

Rejected candidates remain diagnostic-only.

## Queue authority

The scheduler still treats the latest safe candidate set as authoritative. Existing protections remain active:

- stable target identity;
- planner ranking and score preservation;
- current-frame action-button evidence;
- candidate disappearance reconciliation;
- multi-target failure isolation;
- completed-target suppression;
- cooldown and in-flight protection;
- pre-action revalidation;
- guarded dispatch;
- post-action verification.

Automatic Gather/Hunt remains OFF by default.

## Tests

The reconciliation boundary has deterministic JVM coverage for:

1. policy-ineligible candidates being blocked;
2. eligible candidate order being preserved without introducing a second ranking system.

This phase does not claim real-device validation; that requires running the APK against the actual game/device.
